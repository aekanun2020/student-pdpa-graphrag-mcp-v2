# Profile คืออะไร และหน้าตาเป็นอย่างไร

เอกสารนี้อธิบาย profile ซึ่งเป็นสิ่งที่เก็บใน collection `pdpa_profiles` ของ Qdrant
ตัวอย่างทุกรายการเป็นของจริง สร้างจาก [`data/pdpa_knowledge_graph.json`](../data/pdpa_knowledge_graph.json) (190 โหนด / 382 เส้น)
ด้วยฟังก์ชัน `profile_knowledge_graph` ใน [`lightrag/knowledge_graph.py`](../lightrag/knowledge_graph.py) โดยไม่เรียก LLM
(สร้างเมื่อ 22 พ.ย. 2569)

## Profile คืออะไร

Profile คือข้อความย่อสำหรับค้น ทำขึ้นจากกราฟ 1 รายการต่อ 1 ชิ้นส่วนของกราฟ
ชิ้นส่วนของกราฟมี 2 ชนิด profile จึงมี 2 ชนิดตามไปด้วย

| ชนิดของ profile | ทำขึ้นจาก | จำนวน |
|---|---|---|
| profile ของโหนด | โหนด 1 ตัว | 190 |
| profile ของเส้น | เส้น 1 เส้น | 382 |
| รวม | | 572 |

**Profile ส่วนใหญ่ (382 จาก 572) ทำขึ้นจากเส้น ไม่ใช่จากโหนด**
Profile ไม่ใช่ตัวโหนดหรือตัวเส้น โหนดและเส้นตัวจริงอยู่ในกราฟ ซึ่ง server เก็บไว้ในหน่วยความจำ
profile เก็บเฉพาะข้อความย่อของมัน

server สร้าง profile ใหม่ทุกครั้งที่เริ่ม ทั้ง 2 ชนิดมี 4 ช่องเหมือนกัน

| ช่อง | ใช้ทำอะไร | เก็บที่ไหน |
|---|---|---|
| `id` | ถ้าเป็น profile ของโหนด คือ id ของโหนด ใช้เป็นจุดเริ่มเดินกราฟ (seed) ได้ ถ้าเป็น profile ของเส้น คือ `ต้นทาง--ชนิดเส้น--ปลายทาง` ใช้เป็น seed ไม่ได้ | Qdrant (payload) และหน่วยความจำ |
| `keys` | ข้อความสำหรับค้น ต่อกันด้วยช่องว่างแล้วแปลงเป็นเวกเตอร์ด้วย BGE-M3 | Qdrant (เป็นเวกเตอร์ dense + sparse) |
| `value` | ข้อความสำหรับให้ LLM ของ agent อ่าน ใส่ใน context เมื่อ profile ถูกค้นเจอ | หน่วยความจำของ server เท่านั้น |
| `node_category` | บอกชนิดของ profile ชื่อช่องมาจากโค้ด: `prebuilt` คือ profile ของโหนด, `knowledge_relation` คือ profile ของเส้น | Qdrant (payload) และหน่วยความจำ |

Qdrant ไม่ได้เก็บข้อความของ `keys` หรือ `value` เก็บเฉพาะเวกเตอร์กับ `id`

คำว่า high-level กับ low-level ใน README เป็นระดับของคีย์เวิร์ดของคำถาม ไม่ใช่ระดับของ profile
การค้นทั้งสองรอบค้น profile ทั้ง 572 รายการเหมือนกัน ทั้งของโหนดและของเส้น
และ profile ไม่มีช่องใดบอกว่าเป็น high-level หรือ low-level

## ตัวอย่างที่ 1: profile ของโหนด `def_biometric`

```text
id:            def_biometric
node_category: prebuilt
keys:          ["def_biometric",
                "Definition",
                "ข้อมูลชีวภาพ: ข้อมูลส่วนบุคคลที่เกิดจากการใช้เทคนิคหรือเทคโนโลยีที่เกี่ยวข้องกับการนำลักษณะเด่นทางกายภาพหรือทางพฤติกรรมของบุคคลมาใช้ทำให้สามารถยืนยันตัวตน",
                "sec_26 DEFINES",
                "IS_SUBTYPE_OF"]
value:         def_biometric (): ข้อมูลชีวภาพ: ข้อมูลส่วนบุคคลที่เกิดจากการใช้เทคนิคหรือเทคโนโลยีที่เกี่ยวข้องกับการนำลักษณะเด่นทางกายภาพหรือทางพฤติกรรมของบุคคลมาใช้ทำให้สามารถยืนยันตัวตน
               ความสัมพันธ์: sec_26 DEFINES; IS_SUBTYPE_OF: def_sensitive_data
```

### `keys` ทีละชิ้น

| ชิ้น | มาจากไหนในกราฟ | บอกอะไร |
|---|---|---|
| `def_biometric` | id ของโหนด | ชื่อของโหนด |
| `Definition` | ช่อง `label` | โหนดนี้เป็นชนิดบทนิยาม |
| `ข้อมูลชีวภาพ: ข้อมูลส่วนบุคคลที่เกิดจาก…ยืนยันตัวตน` (ข้อความเต็มอยู่ในตัวอย่างข้างบน) | ช่อง `term_th` ต่อด้วย `definition` ตัดที่ 200 ตัวอักษร | คำศัพท์และคำนิยามตามตัวบท |
| `sec_26 DEFINES` | เส้นขาเข้า | มาตรา 26 เป็นผู้นิยามคำนี้ |
| `IS_SUBTYPE_OF` | เส้นขาออก | เป็นชนิดย่อยของโหนดอื่น แต่ไม่บอกว่าโหนดใด |

ข้อความที่ถูกแปลงเป็นเวกเตอร์คือทั้ง 5 ชิ้นต่อกันด้วยช่องว่าง:

```text
def_biometric Definition ข้อมูลชีวภาพ: ข้อมูลส่วนบุคคลที่เกิดจากการใช้เทคนิคหรือเทคโนโลยีที่เกี่ยวข้องกับการนำลักษณะเด่นทางกายภาพหรือทางพฤติกรรมของบุคคลมาใช้ทำให้สามารถยืนยันตัวตน sec_26 DEFINES IS_SUBTYPE_OF
```

ชิ้นที่เป็นภาษาไทยมีชิ้นเดียวคือชิ้นที่ 3 เมื่อผู้ใช้ถามเรื่องลายนิ้วมือ และ LLM แตกคีย์เวิร์ดเป็น
"ข้อมูลชีวภาพ" คำนี้จะใกล้กับเวกเตอร์ของ profile นี้ โหนด `def_biometric` จึงถูกค้นเจอ

### `value` ทีละส่วน

| ส่วน | ความหมาย |
|---|---|
| `def_biometric` | id ของโหนด |
| `()` | ที่สำหรับชนิดของโหนด ว่างเพราะโค้ดอ่านช่อง `type` แต่กราฟเก็บชนิดไว้ในช่อง `label` |
| `ข้อมูลชีวภาพ: …ยืนยันตัวตน` | คำศัพท์และคำนิยาม ตัดที่ 300 ตัวอักษร |
| `sec_26 DEFINES` | เส้นขาเข้า เขียนเป็น "ต้นทาง ชนิดเส้น" |
| `IS_SUBTYPE_OF: def_sensitive_data` | เส้นขาออก เขียนเป็น "ชนิดเส้น: ปลายทาง" |

`value` แสดงเส้นได้สูงสุด 8 เส้น ส่วน `keys` ใช้ 5 เส้นแรก

## ตัวอย่างที่ 2: profile ของเส้น

```text
id:            sec_26--GRANTS_EXEMPTION--sec26_ex1
node_category: knowledge_relation
keys:          ["GRANTS_EXEMPTION", "sec_26", "sec26_ex1"]
value:         sec_26 → [GRANTS_EXEMPTION] → sec26_ex1
```

`id` คือ "ต้นทาง--ชนิดเส้น--ปลายทาง" ข้อความที่ถูกแปลงเป็นเวกเตอร์คือ
`GRANTS_EXEMPTION sec_26 sec26_ex1` ไม่มีคำภาษาไทย เพราะเส้นทั้ง 382 เส้นในกราฟไม่มีคำบรรยาย

## Profile ถูกใช้ตรงไหนของการค้น

1. `search_pdpa` ค้น `pdpa_profiles` 2 รอบ ได้ profile ไม่เกิน 8 รายการเมื่อใช้ค่าเริ่มต้น (ขั้นที่ 2 ใน[รูปขั้นตอนค้น](fig3_search_pipeline.png))
2. โหนด 3 ตัวแรกในผลค้นถูกใช้เป็น seed เดินกราฟ profile ของเส้นถูกข้ามในขั้นนี้ เพราะ `id` มี `--` (ขั้นที่ 3)
3. `value` ของ profile ทุกรายการที่ค้นเจอ ถูกใส่ใน context ใต้หัวข้อ `## ความรู้จาก Knowledge Graph (PDPA)` (ขั้นที่ 6)

## Profile ของเส้นมีประโยชน์แค่ไหน

แทบไม่มี จากผลค้น 70 ครั้งที่บันทึกไว้ใน `eval/unseen28/lab8` ของผู้สอน (รอบทดสอบ 14 พ.ย. 2569 คำถาม 28 ข้อ
ใช้กราฟรุ่นก่อนซึ่งมี 380 เส้น) profile ที่เข้า context มี 488 รายการ เป็น profile ของเส้น 2 รายการ
และการค้น 68 จาก 70 ครั้งไม่มี profile ของเส้นเลย ทั้งที่ profile ของเส้นเป็น 382 จาก 572 รายการของ collection

เหตุคือข้อความที่ใช้ค้นเป็นรหัสล้วน ส่วนคีย์เวิร์ดจาก LLM เป็นคำไทย
ตัวเลขนี้มาจากการทดสอบรอบเดียว นับเมื่อ 22 พ.ย. 2569 จาก context ที่บันทึกไว้ ยังไม่ได้วัดซ้ำกับกราฟ 382 เส้น

## ข้อจำกัดที่ทราบของ profile

- profile ของเส้นแทบไม่ถูกค้นเจอ (ดูหัวข้อก่อนหน้า) แต่ยังถูก embed ทุกครั้งที่ server เริ่ม
- เส้นขาออกใน `keys` เก็บเฉพาะชื่อชนิดเส้น ไม่มีปลายทาง และซ้ำกันได้ เช่น `PDPA_2562` มี `HAS_CHAPTER` 5 ครั้ง
- วงเล็บชนิดใน `value` ว่างสำหรับโหนด 184 จาก 190 ตัว มีค่าเฉพาะโหนดโทษ 6 ตัว เช่น `(อาญา)`
- คำบรรยายใน `keys` ถูกตัดที่ 200 ตัวอักษรกลางคำ เช่น profile ของ `sec_26` จบที่ "ข้อมูลสหภา"
  คำว่า "ข้อมูลชีวภาพ" ซึ่งอยู่ถัดไปในตัวบทจึงไม่อยู่ใน `keys` ของมาตรา 26
- ปลายทางใน `value` เป็น id เช่น `def_sensitive_data` ไม่ใช่คำว่า "ข้อมูลอ่อนไหว"
- profile ของมาตราขึ้นต้นด้วย `####` ซึ่งติดมาจากตัวบทในกราฟ
